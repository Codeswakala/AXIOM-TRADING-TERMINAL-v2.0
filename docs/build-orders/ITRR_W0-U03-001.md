## Executive Summary

The Development Authority has delivered the foundational historical market data ingestion capability for AXIOM.

**Key Achievements:**
- CSV-based historical OHLCV ingestion pipeline
- Normalization, validation, and natural-key upsert into the `candles` table
- Deduplication on reload
- Multi-market support (forex + crypto demonstrated)
- Ingestion run metadata + audit events
- New observability (stats, runs, candle counts)
- 39 automated tests in sandbox
- **Operator verification on real PostgreSQL succeeded** for the core functionality

**Critical Evidence Now Available:**
For the first time in this project, a real PostgreSQL environment was exercised by the Operator. Ingestion of sample data, deduplication, API responses, and persistence all functioned correctly on PostgreSQL.

**One Notable Issue:**
One test (`test_settings_defaults`) failed when running against PostgreSQL because the test hard-coded an assumption that the default database URL starts with "sqlite". This is a test fragility issue, not a functional defect.

**Overall Assessment:**
This unit successfully establishes the first real data ingestion flow in AXIOM. The engineering is sound, governance-compliant, and future-compatible. The Operator verification significantly increases confidence.

## 2. Hypothesis-Driven Investigation

### Primary Hypothesis (from Delivery Report)
> A synchronous, repository-backed CSV ingestion pipeline with UTC normalization and natural-key upsert will reliably load multi-market historical OHLCV, prevent duplicates on reload, and expose run statistics—without requiring live feeds or redesigning the Candle model.

### Counter-Hypotheses Considered by ITRGA
1. Deduplication logic would fail under timezone or floating-point variations.
2. The ingestion service would leak filesystem access or be vulnerable to path traversal.
3. The implementation would be tightly coupled to SQLite and break on PostgreSQL.
4. Partial invalid rows would corrupt the database or cause transaction rollback of valid data.
5. The test suite would pass only because of SQLite-specific behavior.

### ITRGA Hypothesis Evaluation Results

| Hypothesis | Status | Evidence Level | Notes |
|------------|--------|----------------|-------|
| Reliable multi-market CSV load + normalization | **Verified Fact** | Level I (Operator runtime) + Level II (tests) | EURUSD + BTCUSD successful on PostgreSQL |
| Deduplication on reload | **Verified Fact** | Level I | 5 unchanged on reload (both sandbox and PG logs) |
| Partial invalid row handling | **Verified Fact** | Level II | Test `invalid_rows_sample` passed |
| Path traversal protection | **Verified Fact** | Level II | `/etc/passwd` test returned 400 |
| PostgreSQL compatibility | **Supported Inference** | Level I (Operator) | Core path worked; one test assumption broken |
| Scalability for large files | **Unknown** | — | Explicitly out of scope |

**Counter-hypotheses largely falsified** for foundation scope.

### Operator Real PostgreSQL Verification — Level I (Highest Value)

- Two successful sample ingestions via API

**Observed Results:**
- 5 EURUSD candles stored correctly
- Deduplication worked on reload (0 inserted, 5 unchanged)

**One Failure:**
- `test_settings_defaults` failed because it asserts `database_url.startswith("sqlite")` even when the environment variable overrides it.

**ITRGA Assessment:** The functional ingestion path is proven on PostgreSQL. The failing test is a test design issue, not an ingestion defect.

## 6. Consequences, Alternatives & Risks

### Positive Consequences
- First real data now exists in the system.
- Repository layer from W0-U02 is proven in practice.
- Clear extension point for live adapters.

### Risks Introduced / Observed
- **TD-001b** (PostgreSQL verification) is now substantially closed by Operator.
- **TD-013** (row-by-row upsert) — acceptable for foundation; will need bulk path later.
- **TD-014** (naive UTC handling) — noted.
- Test fragility introduced around database URL assumptions.

### Alternatives Evaluated
- Bulk COPY vs row upsert → deferred (correct for this unit).
- Full streaming parser → overkill for foundation.
- Auth on ingestion API → correctly deferred.

### Future Compatibility
- Design supports live feed adapters (via same normalized row + upsert path).
- Multi-market keys are future-proof.
- Ingestion metadata will support future data lineage and replay.
